02 · Overview

Leading five platforms, and stepping in where it mattered

KuCoin set out to replace Zendesk, Ada and other third-party tools with in-house platforms. I led a team of 3 designers across all five platforms and a shared design system. When the most critical one, the agent workspace, left agents stuck, I stepped in to redesign it.

Scope: five platforms, one launch

I scoped every MVP so all five platforms could go live at about the same time. Anything a platform didn't need on day one moved to a later iteration, including the shared empty, loading and error states, which arrived in the second.

A disagreement with developers

Developers were overloaded and wanted simpler interactions; my test was whether the experience still held up for the people using it. We agreed to build the design system first, to settle patterns once and speed up development. The trade-off: UI details such as spacing and type were rough for a while, and caught up once components were synced in design and code.

04 · Design system

Rules, not just components

Built on Ant Design, the system set more than button styles. It set the rules every platform followed, so an agent, a team lead and a compliance officer met the same behaviour wherever they worked. I reviewed every platform against these rules.

1Claim and lockWhoever claims a ticket first is assigned it. One rule, so two agents don't answer the same customer.
2Empty, loading and errorShared from the second iteration, so every table and panel behaves the same when it's empty, waiting or failing.
3PermissionsRoles see different actions, such as edit or view only, and in compliance, different modules.
4One interaction modelOne sidebar, one visual language, and the components B2B tools rely on: buttons, tables and decision trees.
05 · Stepping in · Agent workspace

The busiest platform needed a rethink

When a customer opens KuCoin Support, three platforms work behind the scenes. The agent workspace is where 200+ agents handle chats and tickets all day.

Built
In-house agent workplace Linked to the core system's risk, KYC, trading and account modules.
Before

Third-party tools were costly and inflexible for crypto support work.

Goal

Raise agent efficiency and experience, improve the customer-facing support experience, and replace the third-party stack.

First MVP

Designer A owned the first UI; when agents couldn't use it before launch, I led the redesign with A and B in January 2025.

Why build in-house
  1. 1Built for crypto — workflows shaped for crypto support, not generic ticket templates.
  2. 2Efficiency and experience — agents work faster; customers get better support.
  3. 3Deep integration — risk, KYC, trading and accounts in one place, so agents don't hop systems.
Why I stepped in

The first MVP was built under time pressure, before any agent had tried it. The screens were polished, but the flow was fragmented: in review, agents kept getting stuck, key actions were hidden and the screens didn't follow their workflow. That wasn't a way of working to change overnight. Compliance had just wrapped up, so I brought in designer B, the strongest on flow logic, and with two weeks to the development deadline took over the redesign with A and B.

06 · Research

Watch agents first, then redesign

With only two weeks, I started with observation rather than screens: 5 agents worked on the live MVP, 2–3 per session. We pinned every point of confusion to the screen, then grouped them into three structural blockers.

07 · Three fixes

Three blockers, three fixes

Three blockers explained almost all the friction. I scoped each to one focused change that fit the development deadline.

Where agents got stuck
1
Hidden claim step
4 of 5 agents
2
Context split across tabs
3
Everyday tools hidden in icons
None found them unaided
Fix 2: three side-panel layouts we compared
  • Two zones, collapsible: user info and ticket info in separate areas.
  • Anchor navigation: one long column, with links at the top that jump to each part.
  • Collapsible sections (chosen): one column in the order agents check context: user, history, ticket, each able to expand or fold.

We chose collapsible sections: everything stays in one column, in the order agents read it, and they can fold away what they don't need.

08 · AI assistance

AI that supports the agent's judgment

I set one rule for both AI features: tie them to the ticket in front of the agent, and leave what reaches the customer to the agent. The design followed the Ant Design AI guidelines and a review of competing support tools.

AI reply suggestions

A draft reply, ready to edit

  • Detects the issue and suggests a reply to edit
  • Designed to cut typing and handling time
AI summary

The ticket at a glance

  • Sentiment, issue and a suggested next step
  • Pick up a case without rereading the thread
Where the agent stays in charge
1When it appearsAutomatically, on a customer message, whenever there's something worth suggesting.
2When it's wrongThe agent closes or edits it. Nothing goes out until the agent sends it.
3Sensitive ticketsThe summary flags sensitivity, and the agent handles the case under the team's guidelines.
4The agent sendsEvery reply is reviewed and sent by the agent. The AI never answers a customer on its own.

Still open: agents could close or edit a suggestion, but not regenerate or flag it. I'd add both, so a poor suggestion becomes feedback rather than a dead end.

Mini case study · Diting

Diting: self-serve data for analysts

Turning repeat data requests into templates, so analysts could pull data without writing SQL, and operations could later do it themselves.

Role
Product designer, hands-on on most modules
Team
1 other designer, PM, data engineers
Users
Data engineers and analysts; operations later
Year
2024 · KuCoin

1Context

Analysts and data engineers pull user data for operations, such as the list of users who qualify for a reward campaign. Every pull started as a request and ended as a spreadsheet. The first release served these two roles; later releases would let operations pull data themselves.

2Research: how a request moved

I had calls with users to walk through real requests, then mapped the flow for both data engineers and analysts. A reward request, for example:

  1. Jira request
  2. Confirm on Teams
  3. SQL in HUE
  4. Double-check
  5. Confirm with business
  6. Upload or email

What slowed it down

  • Repeat requests, such as reward lists, rewritten in SQL each time
  • Manual checks against reward amounts, or cross-checks with data engineering
  • Exports capped at 50,000 rows, so large pulls were split into parts
  • Results passed around by email

3Scope

The PM planned four modules, and I worked to the delivery order: data tools first, then the data service (APIs), with data assets and a data map opening data to operations later. Before designing, I also reviewed comparable data platforms, such as DataLeap.

4Design

Templates for repeat requests

A common request becomes a template. Running a task shows only the parameters it needs, then sends the result to the reward platform or by email automatically.

Create a template, run a task from it, track progress. Red notes mark the auto-filled parameters and the automatic hand-off.

Self-serve query, no SQL

Pick a data model and columns, then combine and/or filters. Built for analysts first, and ready to open to operations later.

Data map to find data

One search across tables, tasks, topics and APIs, grouped by business line. Admin pages cover accounts, roles and menus, with logs for auditors.

5What I learned

Walking through real requests mattered more than starting from a feature list. The template idea came from seeing the same reward request rewritten again and again.

Diting wasn't a company priority, and no usage data was collected.
09 · Result

Ready to pilot, not yet measured

Over six months, the team delivered five platforms on one shared design system, and the redesigned agent workspace was ready for a 20-agent pilot. Before the pilot ran, the team was restructured and I moved to a customer-facing project, so there is no usage data.

How I'd measure it

10 · Reflection

What I'd keep, and what I'd change, as a lead

1
Match designers to the problem, not only their strength

Matching by strength worked for compliance and the design system. On the agent workspace, a flow-heavy tool, strong visuals alone weren't enough. Next time I'd pair visual and flow skills on the busiest platform from the start.

2
Watch users before the MVP, not after

Skipping early validation left the MVP out of step with how agents work, so it needed rework and cost development time. Watching real users is the fastest path to clarity.

3
Still open: measure from day one

Without a baseline, the redesign's value rests on review feedback. Next time I'd set time to first reply and claim errors before the MVP ships, so any redesign can be judged against them.
